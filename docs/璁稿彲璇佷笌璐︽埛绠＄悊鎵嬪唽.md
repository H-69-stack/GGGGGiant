# 同济大学-捷安特管件设计软件 · 许可证与账户管理手册

> 适用版本：1.0.0　｜　部署形态：客户局域网中心服务器（Docker）+ 浏览器访问
>
> 本手册面向三类读者：
> - **开发/发证侧**（你和你的维护团队）：如何签发、续期、升级许可证，如何管理私钥。
> - **现场部署/维护侧**：如何在客户服务器上安装、激活、排障。
> - **客户使用侧**：如何获取机器码、安装许可证、注册与使用账户。

---

## 1. 整体设计：防盗是怎么做到的

软件采用「**签名许可证 + 硬件绑定 + 局域网访问控制**」三重防护：

1. **签名许可证（防伪造、防篡改）**
   - 每份许可证由开发侧用 **私钥（Ed25519）** 签名；客户端只内置 **公钥** 用于验证。
   - 客户即使拿到全部文件，也无法伪造或修改许可证（任何改动都会导致签名失效）。
   - 许可证内写明：客户名称、**到期日期**、**允许注册的账户类型**、绑定的**服务器机器码**。

2. **硬件绑定（防整体拷走盗用）**
   - 许可证绑定到服务器的**硬件指纹**。当前算法以 Windows 系统安装标识（MachineGuid）为**单一强标识**，首次采集后在本机锚定，详见 3.6。
   - 把整套软件拷到另一台机器，机器码不匹配 → 拒绝运行。

3. **局域网访问控制（防外部访问）**
   - 服务只在客户内网提供，**不暴露公网端口**。
   - 应用层再加一道 **IP 网段白名单**：只放行客户局域网网段，非授权网络一律 `403` 拒绝。

> **诚实说明（务必理解）**：没有任何方案能 100% 防止"拿到 root 权限的客户"破解本地软件。
> 上述措施的目标是把破解成本抬到远高于购买成本，**挡住绝大多数非专业盗用**，
> 配合**法律合同**形成完整保护。可选的「加固镜像」(Nuitka 编译) 会进一步抬高门槛。

### 账户类型（工作角色）

| 账户类型 | 可访问功能 |
|---|---|
| ALL | 全功能（工艺规划 + 模具设计 + 硬模成型 等全部） |
| 工艺规划 | 工艺规划/工艺优化相关模块 |
| 模具设计 | 模具设计相关模块 |
| 硬模成型 | 硬模成型相关模块 |

许可证可指定**允许注册哪些账户类型**。例如签发"硬模成型 + 工艺规划"的许可证，
该客户就只能注册这两类账户，且账户有效期由许可证到期日期决定。

## 2. 名词速查

| 名词 | 含义 |
|---|---|
| 机器码 | 服务器硬件指纹的短展示形式，形如 `6ECF1-D9F4A-B3331-3F00A`。客户提供给你用于发证。 |
| 许可证文件 | `license.dat`，由发证工具签发，放到服务器生效。 |
| 私钥 | `private_key.pem`，**绝密**，只在你的发证工具里。泄露=防盗失效。 |
| 公钥 | 内置在客户端中，用于验签，可公开。 |
| 发证工具 | 开发/维护侧专用程序（GUI `gt-license-tool` 或命令行 `issue_license.py`）。 |
| 机器码工具 | 客户在服务器上运行的小程序（`gt-machine-code`），用于读取机器码。 |

## 3. 开发/发证侧操作指南

### 3.1 一次性准备：生成发证密钥（极重要）

整个体系的根基是一对密钥。**只需在最开始做一次**。

```bash
cd tools/license_authority
python generate_keys.py            # 或 python generate_keys.py --password 你的口令
```

执行后：
- 生成 `tools/license_authority/keys/private_key.pem`（**私钥，绝密**）。
- 生成 `tools/license_authority/keys/public_key.pem`（公钥）。
- 自动把公钥写入客户端 `backend/core/common/licensing/public_key.py`。

> **私钥管理铁律**
> 1. 私钥**绝不**放进客户端、安装包、Git 仓库（已在 `.gitignore` 排除）。
> 2. 离线备份私钥（如加密 U 盘）。私钥丢失=无法再签发/续期，只能换新密钥并重发所有客户。
> 3. 私钥泄露=任何人可伪造许可证。若泄露，需重新生成密钥并给所有客户重新发证。
> 4. 建议生成时设置 `--password` 口令，进一步保护私钥。

> **重新生成密钥的后果**：会使**所有已签发的旧许可证全部失效**。仅在初次部署或私钥泄露需吊销时才做。

### 3.2 把发证工具打包成 exe（给维护团队）

```bat
cd tools\build
build_license_tool.bat
```
产出 `dist\tools\gt-license-tool.exe`。把它发给维护人员时：
- 在 exe 同级建立 `keys\` 目录，放入 `private_key.pem`。
- **严禁**把私钥或该 exe 交给客户。

### 3.3 签发一份新许可证（图形界面）

1. 双击 `gt-license-tool.exe`。
2. 填写：
   - **客户名称**：如"某某管业"。
   - **机器码**：客户提供的机器码（如 `6ECF1-D9F4A-B3331-3F00A`）。
   - **允许的账户类型**：勾选（勾 ALL = 全功能）。
   - **到期日期**：用 `+3个月/+1年` 快捷按钮或手填 `YYYY-MM-DD`。
3. 点「生成许可证」，保存为 `license.dat`。
4. 点「验签自检」确认签名有效。
5. 把 `license.dat` 发给客户。

### 3.4 签发许可证（命令行，便于批量/脚本）

```bash
cd tools/license_authority
python issue_license.py \
    --customer "某某管业" \
    --machine-code 6ECF1-D9F4A-B3331-3F00A \
    --roles 硬模成型,工艺规划 \
    --expires 2027-06-30 \
    --out issued/某某管业_license.dat
```
- `--roles ALL` 表示全功能；多个用逗号分隔。
- 自检：`python issue_license.py --verify issued/某某管业_license.dat`

### 3.5 常见维护场景

| 场景 | 操作 |
|---|---|
| **卖给新客户** | 拿到新客户机器码 → 用发证工具签发一份新 `license.dat` → 发给客户。 |
| **客户要加账户类型** | 用同一机器码，勾选更多账户类型，重新签发 → 客户替换 `license.dat`。 |
| **续期（到期前/后）** | 「载入旧许可证」自动回填 → 改到期日期 → 重新生成 → 客户替换文件。 |
| **客户换服务器** | 让客户在新服务器取新机器码 → 按新机器码重新签发。 |

> 所有"修改"本质上都是**重新签发一份新的 `license.dat` 让客户替换**。替换后**无需重启**，软件会自动重新加载。

### 3.6 机器码升级说明（新指纹算法）

> **一句话结论**：新版本起，机器码改为「**Windows 系统安装标识（MachineGuid）单一强标识 + 首次锚定**」算法，
> 与旧版机器码**不兼容**。升级前已签发的许可证会提示「机器码不匹配」，这是预期行为，需要客户按新机器码**重新签发**。

**为什么变**

- 旧算法把主板/产品 UUID、磁盘序列号、网卡 MAC、CPU 标识等多源信息混合哈希；其中任何一项变化
  （换网卡、插拔硬盘、容器重建、系统更新）都可能改变机器码，导致同一台服务器频繁"变码"。
- 新算法优先只使用 Windows 安装时生成、重装前不变的 `MachineGuid`
  （注册表 `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid`）作为强标识；
  首次采集后在本机锚定存档，之后即使网络、容器变化，机器码也保持不变。
- 仅在完全拿不到系统标识的极端情况下，才退回其它信息，并在界面明确标记「不稳定」。

**影响面**

- 新旧机器码**不相同**；旧 `license.dat` 在新版本上会提示机器码不匹配，**不是许可证损坏**。
- 因此，升级到新版本后，每个客户都需要重新取一次机器码并重新签发许可证（用户侧已确认接受）。
- Docker 部署场景：`.env` 里的 `GTAPP_HOST_FINGERPRINT` 是宿主机机器码的注入值。升级后请重新运行部署脚本
  （或按新算法重新生成）刷新该值，否则容器内仍沿用旧指纹，会与机器码工具显示的新机器码不一致。

**重新签发步骤**

1. 客户在「软件激活」页点「复制机器码」（未授权时软件启动会自动进入该页），把**新机器码**发给供应商。
2. 供应商用发证工具（GUI，或 3.4 命令行 `issue_license.py --machine-code`）按新机器码签发新的 `license.dat`。
3. 客户用新文件替换 `license/license.dat`，刷新页面即可生效，**无需重启服务**。
4. 供应商在签发记录中备注「机器码算法升级，重签」便于日后核对。

**稳定性说明（请对客户强调）**

- 同一台服务器上，**重启、切换网络、插拔 U 盘、容器重建（标准部署脚本已注入宿主机机器码）、升级本软件版本都不会改变机器码**；
  首次运行生成的 `license/machine_anchor.json` 就是这套锚定记录，请随 `license/` 目录一起保留（备份、迁移时注意）。
- 迁移/克隆到新机器时**不要**把旧机器的 `license/machine_anchor.json` 一起拷过去（连同旧 `license.dat` 一起作废）；
  新机器首次运行会重新锚定并生成新机器码，按新机器码重新签发即可。
- **更换主板、重装 Windows、把系统克隆迁移到新机器**会改变机器码，此时必须重新取码、重新签发。
- 若页面出现黄色提示「本次采集未拿到稳定系统标识，机器码可能变化，请联系供应商」，
  说明该机器未能读到稳定的系统标识（如极端精简/受限系统），请先联系供应商排查，确认稳定后再发证。
- 发证时务必使用**当前**机器码；不要复用升级前的旧机器码。

## 4. 客户使用侧操作指南

### 4.1 安装软件（中心服务器）

**前置条件**（建议由客户 IT 完成）：
- 一台 Windows 服务器（Win10/11 或 Windows Server）。
- 已安装并启动 **Docker Desktop / Docker Engine**。

**安装步骤**：
1. 双击 `GiantTubeAppSetup.exe`（Inno Setup 安装包），按提示安装。
2. 安装程序会自动构建并启动服务（首次较慢，请耐心等待）。
3. 也可手动部署：以管理员身份打开 PowerShell，在程序目录执行：
   ```powershell
   powershell -ExecutionPolicy Bypass -File deploy\windows\install.ps1
   ```
4. 安装完成后，局域网内任意电脑用浏览器访问：`http://服务器IP:5880`。

### 4.2 获取机器码并激活

1. 打开软件：未授权时会自动进入「软件激活」页，页面中间显示「本机机器码」，点「复制机器码」。
   - 已授权后，管理员可在「部署与授权」页查看机器码（含复制按钮与稳定状态/来源）。
   - 或在服务器运行 `dist\tools\gt-machine-code.exe`，窗口会显示机器码。
   - 机器码下方会注明是否已「锚定」：正常应显示已锚定（重启/换网络不变）；
     若显示黄色「机器码可能变化」，请先联系供应商排查，**不要**直接发证。
2. 把机器码发送给软件供应商。
3. 收到供应商回传的 `license.dat` 后，放到：
   ```
   程序目录\license\license.dat
   ```
4. 刷新页面（或重新打开软件）：许可证生效，自动进入登录页。**无需重启服务**；
   管理员可在「部署与授权」页确认授权状态。

### 4.3 注册与使用账户

1. 用默认管理员登录（账号 `admin`，初始密码见交付说明，**首次登录请尽快修改**）。
2. 进入「注册新用户」：
   - 系统会根据许可证**自动只显示允许的账户类型**。
   - 密码要求：至少 8 位，含大小写字母、数字、特殊字符。
3. 注册成功后即可用新账户登录，访问对应功能模块。

> 若注册页提示"许可证未授权该账户类型"，说明该类型不在许可范围内，请联系供应商升级许可证。

### 4.4 局域网访问限制

- 默认只允许**局域网网段**访问，外部网络会被拒绝（`访问被拒绝：当前网络不在授权的局域网范围内`）。
- 如需限定到更小的子网（如只允许 `192.168.10.0/24`），请联系供应商/IT 调整（见 5.3）。

## 5. 部署/维护侧进阶

### 5.1 目录与文件一览

| 路径 | 说明 |
|---|---|
| `backend/core/common/licensing/` | 许可证核心（验签、指纹、管理器）。 |
| `backend/core/common/licensing/public_key.py` | 内置公钥（由 generate_keys 写入）。 |
| `license/license.dat` | 客户现场的许可证（挂载进容器 `/app/license`）。 |
| `license/machine_anchor.json` | 首次运行自动生成的机器码锚点（仅含脱敏分量）。**不要手工编辑、不要复制到别的机器**；正常重启/升级无需删除。 |
| `tools/license_authority/` | 发证工具（私钥、签发脚本、GUI）。 |
| `tools/machine_code/` | 机器码采集工具。 |
| `deploy/windows/` | Windows 部署脚本与 Inno Setup。 |
| `docker/backend.hardened.Dockerfile` | 可选：Nuitka 加固镜像。 |

### 5.2 硬件指纹与容器的注意点（关键）

容器内看到的硬件信息与"宿主机"可能不同，且容器重建后可能变化。因此：
- 部署脚本 `install.ps1` 会用机器码工具计算**宿主机指纹**，写入 `.env` 的 `GTAPP_HOST_FINGERPRINT`。
- 容器通过该环境变量获得稳定指纹，**重建容器也不变**。
- 发证时务必使用**宿主机**机器码（登录页/机器码工具显示的就是它）。

### 5.3 收紧 IP 白名单到客户子网

编辑程序目录下 `.env`：
```env
GTAPP_ALLOWED_CIDRS=192.168.10.0/24
```
然后重启：`docker compose up -d`。
- 多个网段用逗号分隔：`192.168.10.0/24,192.168.20.0/24`。
- 排障时可临时关闭白名单：设 `GTAPP_IP_ALLOWLIST=0`（排障后务必改回 `1`）。

> 真实客户端 IP 由 nginx 透传（`X-Real-IP`/`X-Forwarded-For`）。若在某些 Docker 网络下所有客户端 IP 都显示为网关地址，请联系部署方调整网络模式（如 host 网络）或仍以"不暴露公网端口"为主要防线。

### 5.4 可选：启用加固镜像（Nuitka 编译核心代码）

进一步防止客户阅读/篡改 Python 源码：
```powershell
powershell -ExecutionPolicy Bypass -File deploy\windows\install.ps1 -Hardened
```
或手动：
```bash
docker build -f docker/backend.hardened.Dockerfile -t giant-tube-app-backend:latest .
docker compose up -d
```
> 该步骤较重、依赖构建环境，**首次启用请在构建机上验证通过**再交付。

### 5.5 查看启动信息与许可证状态

```bash
docker compose logs backend | grep 机器码
```
后端启动时会打印：机器码、许可证是否有效、到期日期、授权账户类型。

## 6. 故障排查（FAQ）

| 现象 | 原因与处理 |
|---|---|
| 登录页显示"未找到许可证文件" | `license/license.dat` 未放置或路径不对，放好后刷新。 |
| "许可证签名无效（可能被篡改…）" | 文件被改动或损坏，重新向供应商索取原始文件。 |
| "许可证未授权给本服务器（机器码不匹配）。若本机机器码近期发生变化，请复制当前机器码重新申请/签发许可证" | 发证时用的机器码与本机不符。**升级到新指纹算法后，旧许可证必然出现此提示**，按 3.6 取新机器码重新签发即可。重启/换网络不会变；换主板/重装系统才会变。 |
| "许可证已于 … 到期" | 续期：供应商重发新 `license.dat` 替换。 |
| 注册时"许可证未授权该账户类型" | 该账户类型不在授权范围，升级许可证。 |
| 外部/某些机器访问被拒绝 | IP 不在白名单。确认在局域网内，或联系调整 `GTAPP_ALLOWED_CIDRS`。 |
| 功能模块返回 403、提示未授权 | 许可证无效（过期/缺失/机器不匹配），先解决许可证。 |

## 7. 安全与合规建议

1. **私钥**离线妥善备份，设置口令，绝不入库/外发。
2. 交付合同中明确**软件著作权、授权范围、禁止逆向/再分发**条款。
3. 给客户的默认管理员密码应在首次登录后立即修改。
4. 定期审视已签发许可证清单（`tools/license_authority/issued/`，本地保存，勿入库）。
5. 重大版本/密钥变更前，先在测试环境验证再推送给客户。
